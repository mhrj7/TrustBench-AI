# Handover (TB-054)

What a maintainer needs to pick TrustBench up: where it stands, what is evidenced and what is open, which failure modes
are unresolved, what is supported, what to run next and what should trigger maintenance. Numbers are not restated here;
they live in the generated reports and evidence files linked below, so this page cannot drift from them. The Core-task

agent security in general.

## Where the project stands

- **Release:** v1.0.0, <https://github.com/mhrj7/TrustBench-AI/releases/tag/v1.0.0>, tagged on `c831245`. Assets: the
  source archive, report, claim register, reproduction manifest, release-check record, license and third-party notices,
  with `SHA256SUMS`. Verified from the public links (`evidence/tb053-release.json`): every checksum matches, the key and
  personal-path scan is clean, and the quickstart runs from the downloaded archive in a clean Debian 12 container.
- **Release history:** `evidence/release-gate-ledger.json` records every Tier 2 attempt, one per candidate. Two passed
  (`7518c85`, the TB-051 candidate; `c831245`, v1.0.0), one failed (`dd4e8de`, the validity invariant: provider timeouts
  made too many pairs invalid) and five have no recorded outcome because the candidate was superseded first (the
  per-candidate records are `release/superseded-*.json`).
- **Results and claims:** the technical report is `research/report.md` and what may and may not be claimed is
  `research/claims.md`; both are generated from stored artifacts and checked (`npm run claims:check`, `npm run report:check`).
- **Reproduction:** `repro/README.md` rebuilds every published number from the committed raw records in a clean container.
- **Live service:** <https://trustbench.taila273c6.ts.net>, self-hosted on one machine behind Tailscale Funnel
  (`docs/deployment-runbook.md`). Best effort: when it is down, everything it shows is in the repository.
- **Open limits register:** `docs/known-issues.md` (research, measurement, gateway and engineering items, each marked
  open, partly addressed, measured or fixed). This handover summarises the open ones; the register stays the source.

## Unresolved failure modes

Grouped by what they limit. The `docs/known-issues.md` IDs carry the detail and evidence.

**What the result covers**

- One frozen configuration (`gateway_directive_flow_v4` on `nvidia:openai/gpt-oss-20b`, plain prompt profile) and static
  attack renderings (`docs/frozen-config.md`, `research/claims.md`). Generalisation to other models, workflows and attack
  families is a hypothesis; on new attack families the interval includes zero.
- No adaptive attacker was tested; static benchmarks can overstate efficacy (claims register).
- Holdout-1 on its own is not separated; the effect rests on the pre-declared pooled analysis.
- Which layer causes the improvement is not separated: the provenance-aware layer versus capability scoping
  (development ablation interval reaches zero; no confirmatory capability-only arm).
- Pilot-sized evidence with wide intervals (R5); a thin holdout designed after development results were seen (R6, R7).
- The gateway's advantage depends on an undefended baseline whose tool backend is permissive (M5); when the tool service
  enforces the task contract itself, the gateway adds little.
- "Unsafe effect" counts out-of-allowlist reads as unsafe; treating read-only faults as safe shrinks the difference
  (M4, `research/label-audit.md`).
- Some models never read the injected text, so no defense effect is measurable on them (M7).

**Defense behaviour**

- A false value stated as plain fact inside an authorized document (`TB-ATT-DOC-005`) passes every directive-flow
  version; closing it needs an independent trusted source (R2).
- Context contamination: an adjacent injected instruction can relabel a legitimate sentence and block a correct answer (M11).
- False positives on contract-conformant notes and drafts, including benign tasks (M12).
- The classifier-based defenses are stochastic; sticky denials only partly contain retries (M2).
- Provenance labels record lineage, not authenticity, and free-form model text mixes sources (G4); identifiers are
  matched exactly, with normalization gaps tested but not proven absent (G6).

**Measurement and evaluation**

- Hosted model aliases are not pinned snapshots and Gemini rejects `seed` (M2).
- The exact-answer oracle is strict ("synthetic Silver" fails "Silver"), which costs some systems utility (M13).
- The evaluator's labels were audited by AI reviewers only; no human review (claims register; M10 for attribution).
- Approval is synthetic in automated runs; no study of human approval behaviour (G1).

**Engineering**

- Exactly-once writes hold only for local SQLite actions; there is no claim for external APIs (G2).
- LangGraph covers only the approval workflow; the agent loop is a custom state machine (G5).
- The review site is a redacted static export with no authentication (E7).
- On the author's machine Ollama listens on all interfaces until the app setting is turned off (E3, host setting).
- The live service runs on one machine: no redundancy, and the daily shared budget can run out (`docs/live-service.md`).
- Free-tier provider timeouts can invalidate a live gate attempt (the `dd4e8de` failure); the gate is capped at one
  attempt per candidate on purpose, so such a candidate must be superseded rather than rerun.

## Next experiment

The claims register names what would test each open hypothesis. In order of what it would settle:

1. **A confirmatory holdout with a capability-only arm**, pre-registered before it runs, to separate the
   provenance-aware layer from capability scoping.
2. **An adaptive attacker** (black-box or optimisation-based) against the frozen gateway, since the current attacks are
   static renderings.
3. **More holdout tasks or repetitions**, so holdout-1 can be judged on its own.
4. **External agent validation (TB-055 to TB-066, next in the workbook):** select an independent open agent, wrap its
   tools behind the gateway, pre-register the protocol, and run the paired evaluation on it. This tests whether the
   result transfers to an agent not written for TrustBench.

Any of these needs a recorded amendment in `protocol/amendments.md` before its first run; frozen files cannot change
without one (`npm run verify:frozen`).

## Maintenance triggers

Event → what to do. Each step is an existing script or runbook section.

| Trigger | Action |
| --- | --- |
| Any push or pull request | Tier 1 release gate runs in CI (`docs/release-gate.md`); a verdict regression or a more permissive policy trail blocks it |
| A release candidate | All ten release checks (`scripts/release-check.py`) and one Tier 2 live attempt; a failed or interrupted candidate is superseded, never rerun |
| Any change under `web/src` or to the public text | Rerun `scripts/check-claims.py` and `scripts/build-report.py` and commit what they rewrite, or the clean reproduction flags the change |
| A provider changes a model behind its alias, or rate limits or the free tier change | Re-run the development smoke and dry runs (`sh bin/trustbench benchmark dev-frozen --dry-run`); never rerun sealed holdouts; record the change in `docs/known-issues.md` (M2, M9) |
| Node, npm, uv or Python version bump | Update the pinned versions, re-run `npm run verify` and `scripts/check-readme.py --fresh`, then update this table |
| Dependency or lockfile update | `npm run verify`; the hash-pinned manifest (`sh bin/trustbench manifest`) must stay unchanged or be amended |
| An evaluator, oracle or frozen-config change | Pre-register an amendment first (`protocol/amendments.md`), then `npm run verify:frozen` |
| Live service down, out of budget, abused, or a key leaked | `docs/deployment-runbook.md`, "Operating it": health, spend, key rotation, run removal |
| Before a risky deployment change | Back up the demo's data (`sh deploy/backup-demo.sh`); roll back with the previous image (runbook, "Backup and rollback") |
| A known issue changes status | Update `docs/known-issues.md` and, if a claim changes, the claim register, then `npm run claims:check` |
| Workbook edits | Recalculate and save in Excel, then `npm run verify:workbook` (`scripts/check-workbook.py`) and `scripts/check-handover.py` |
